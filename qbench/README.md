# qbench — стенд для замера КАЧЕСТВА кода, а не дисциплины сессии

Комплект `trah-setup` целиком про то, как ведётся сессия: экономия контекста,
запись на диск, гарды, сжатие. Про то, каким выходит **код**, в нём нет ни
одного куска. Этот стенд существует, чтобы такие куски писались по замеру, а
не по убеждению.

Правило у стенда одно: **число или ничего**. Всякое утверждение вида «так код
станет лучше» здесь обязано опираться на парный прогон одних и тех же задач с
изменением и без него. Иначе это заявление о несуществующей альтернативе —
ровно то, на чём в июле 2026 сгорел `rtk`: инструмент отрапортовал 96,2 млн
«сэкономленных» токенов, а измеренный счёт в 425 прогонах JetBrains ВЫРОС,
медиана +7,6% (p=0,004).

## Как устроено

Три стенда, по нарастанию того, что они ловят.

| | что за задача | что меряет |
|---|---|---|
| `bench.py` | добавить подсчёт суммы инвентаря | базовые привычки: смотрел ли соседей, переиспользовал ли `parse_price`, гонял ли проверки |
| `bench2.py` | добавить формат отчёта `json` | работу по конвенциям, которые видны ТОЛЬКО из кода: реестр `@register`, идиома лога, общие фикстуры, changelog |
| `bench3.py` | отсеять снятые с продажи позиции | вкус: у задачи есть дешёвый неправильный ответ, проходящий тесты — размазать предикат по трём рендерерам вместо одного места |

Каждый стенд раскладывает свой эталонный репозиторий, коммитит его, запускает
`claude -p` в нём и разбирает результат **машиной**: стенограмму (какие
инструменты и в каком порядке звались ДО первой записи), git-дифф, запуск
собранного кода, `ruff`, `pytest`.

`judge.py` — отдельный судья вкуса по рубрике Senior SWE-Bench: оси
`minimality / approach / hygiene / fluency / craftsmanship / practice_alignment`,
оценки A–F, вердикт «сеньор смёржил бы как есть». Судит **другая модель**
(по умолчанию `claude-fable-5-1`), видит только репозиторий и дифф — ни
условия прогона, ни стенограммы.

`briefs/*.md` — тексты-кандидаты, которые подаются подопытной сессии как
проектный бриф (`--brief`). Это и есть то, что мы проверяем: помогает ли текст,
и какой именно.

## Запуск

Один раз — окружение для эталонных репозиториев:

```bash
uv venv venv && uv pip install --python venv/bin/python pytest ruff
```

Дальше условие целиком — одной командой (N параллельных прогонов):

```bash
BENCH=bench3.py ./batch.sh base 5                          # без брифа
BENCH=bench3.py ./batch.sh principles 5 --brief briefs/principles.md
python3 judge.py runs/base-* runs/principles-*             # судья вкуса
```

Модель и усилие — переменными: `QBENCH_MODEL` (по умолчанию `claude-opus-5`),
`QBENCH_EFFORT` (по умолчанию — умолчание модели), `QBENCH_JUDGE`.

Прогоны ложатся в `runs/` и в git не идут: каждый — это целый репозиторий.
В git идут только измеренные итоги, в `results/`.

## Что уже измерено

`results/2026-09-12-opus5-baseline.md` — базовая линия Opus 5 без брифа.
Короткий вывод: механические привычки у модели УЖЕ есть (20 из 20 признаков
на `bench2`), а судья вкуса ставит 4,43 из 5 и мёржит как есть лишь 1 прогон
из 5. Единственная ось, где стабильно провал, — минимальность.

Отсюда следствие для комплекта: хуки-заслоны на «посмотри перед записью» и
«не дублируй» ловили бы пустоту. Работать надо с тем, что модель добавляет
лишнее, — а это правится текстом и вторым проходом, не гардом.
